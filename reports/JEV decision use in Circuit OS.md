# Put Jev on the gates, never the generator

Jev fits Circuit OS well in one specific role: it answers small, typed questions (yes/no, pick one label, score on a rubric) at the points where your pipeline currently has **no decision at all**, or where the LLM grades its own work. It cannot write a DesignSpec, a CircuitIR or a patch, because it only chooses among, scores or affirms options you define in advance ([PyPI typesafe-sdk](https://pypi.org/project/typesafe-sdk/)). That makes it compatible with the One Rule by construction. The highest-value uses, in priority order, are: a scope/template router in front of `intent_parser.py`, the "out of my depth" signal that Phase 2 free-form generation explicitly needs, a rubric judge for explanation quality in CI, a net-class and placement-role classifier that feeds the Phase 3 constraint layer, and a commit-time check that catches decisions nobody logged. It should never decide anything that `ir_validator.py`, `HardwareRuleEngine`, the SPICE grader, the BOM matcher or footprint inference already decide, and it should only ever **add scrutiny, never remove it**. One caveat comes before any of this. You believe you are near the end of Phase 2, but the local repo says Phase 2 has not started. The priorities below are built to hold either way, but reconciling the two views is worth an hour before you commit Phase 3 work.

## Jev is a calibrated chooser, and many of its facts come from snippets

The integration surface is small and verified from first-party package code. There is one endpoint, `POST https://api.typesafe.ai/v1/systemone`, which takes a `state` (text or JSON) and a named set of questions. Each question is a **Noul** (probability that a statement is true), a **Choice** (one label from a fixed set, with per-label probabilities and a `confidence`), or a **Score** (a probability-weighted position on an ordered rubric). All questions are answered in parallel in one call. The official Python package is `typesafe-sdk` (v0.7.1, 21 Sept 2026, MIT). It provides sync and async clients, a typed error hierarchy, a 10-second default timeout and the `TYPESAFE_API_KEY` env var. Its schema states that "output tokens are currently free of charge" ([PyPI typesafe-sdk](https://pypi.org/project/typesafe-sdk/)). A TypeScript SDK, `@typesafe-ai/sdk` 0.6.0, also exists ([npm](https://www.npmjs.com/package/@typesafe-ai/sdk)). The `typesafe-ai` package on PyPI is **not official**. It is a defensive squat, registered because AI assistants hallucinate that name ([PyPI typesafe-ai](https://pypi.org/project/typesafe-ai/)). Pin `typesafe-sdk` exactly: it went from 0.0.1a0 to 0.7.1 in twelve days.

Everything else comes from **search-result summaries only**, because the proxy blocked typesafe.ai, its docs and most press pages. That includes the following claims:

- Limited early access began 15 Sept 2026, alongside a $40M seed round ([Wikipedia](https://en.wikipedia.org/wiki/Jev_(AI_model)); [TypeSafe blog](https://typesafe.ai/blog/introducing-system-one-models-and-jev)).
- Price is **$0.042 per 1M input tokens** ([MindStudio](https://www.mindstudio.ai/blog/jev-pricing-cost-per-token)).
- Latency is **70–500 ms** ([AlphaSignal](https://alphasignal.ai/news/pydantic-ai-adds-jev-to-cut-classification-latency-6x-without-generating-tokens)).
- Context is capped at roughly 32k tokens per state-plus-question branch ([community gist](https://gist.github.com/pjburnhill/adf8d28efcad9df037bfdece178ef965)).
- Native Pydantic AI support exists as `typesafe:jev-latest` ([Pydantic docs](https://pydantic.dev/docs/ai/models/typesafe/)).
- The vendor claims it is "193x faster, 445x cheaper" ([Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/typesafe-ais-jev-offers-an-alternative-to-llms-that-claims-to-be-193x-faster-and-445x-cheaper-system-one-type-model-is-bespoke-for-probabilistic-decision-making)).

Independent tests found gains closer to **4–7x faster and 31–65x cheaper** than frontier models ([DEV Community](https://dev.to/arifulislamat/typesafes-jev-model-is-it-really-193x-faster-and-444x-cheaper-56oa)). Critics also note that the vendor's evals were scored against labels generated by other LLMs ([Cherry Creek News](https://thecherrycreeknews.com/typesafe-jev-system-one-model-claims-evals-independent-tests-cherry_creek/)). No independent calibration study exists, and nobody has benchmarked Jev on electronics prompts.

Taken at face value, cost does not matter: a 2,000-token state costs about $0.00008 per call. What matters is **latency well inside your 15-second generation budget** and **per-answer probabilities you can threshold**. The risks that matter are also concrete. The vendor is nine days old, availability is gated, nothing is known about data retention or SOC 2, and every prompt you send it leaves your infrastructure. Treat every Jev call as optional, with a deterministic or Claude fallback, and measure calibration on your own golden set before trusting any threshold.

Jev is also a **second AI provider**, and your rules say AI modules use Anthropic `tool_use`. Adopting it is a logged decision in its own right. It needs an entry in `brain/decisions.md`, with the fact that it chooses but never generates as the stated reason it does not breach the One Rule. It also needs an **optional** `TYPESAFE_API_KEY` in `core/config.py`, because config fails fast on missing required vars. The new module must be registered in `regen_state.py` and `progress_gen.py` in the same commit. Tests should auto-skip live calls the way `requires_api` already does. Rate limits stay on the routes that call it.

The rule engine and the simulation grade are advisory and never block persistence. `Component.confidence` is populated but gates nothing, and a grep finds no threshold anywhere (`circuit_os_decision_points` Q3). Jev belongs at the gaps where the input is natural language or a judgment call, which is exactly where deterministic code cannot reach. It all fits into one module, for example `backend/ai/decision_gates.py`, which returns Pydantic results carrying the raw probabilities so they can be persisted to PostgreSQL next to the design.

Give it a structured schema first, with per-component `why`, `what_breaks` and `uncertainty` fields, so Jev scores fields rather than prose. Second, like `scripts/review_panel.py`, a Jev score is a pre-screen. It **cannot close criterion 12**, which requires human reviewers.

## Phase 3 constraint layer: Jev labels nets, deterministic rules write constraints

Phase 3 is settled on paper. The plan is to integrate freerouting rather than extend the A* engine, and to make the differentiator "the constraint layer — net classes, differential pairs and keepouts derived from SignalType and ApplicationClass, each carrying a plain-English reason" (`brain/decisions.md:369-374`). Only `to_dsn()` exists so far (`backend/pcb_engine/router.py:499-507`). The constraint layer is a stack of classification decisions followed by deterministic rule application, so Jev's job is narrow. It supplies a **label** when the IR does not already determine one. A lookup table keyed on that label then produces the width, clearance, pairing, keepout and the plain-English reason. Jev cannot write the reason, and it should not: a reason generated by a lookup table is reproducible and auditable, and one generated by a model is not.

Most nets in a Phase 1 template are already classified by `SignalType`, so C1's real value arrives with free-form designs and parts outside the constraints dict. Storing the probability in each constraint record also answers a question PCB_STRATEGY names as a way the strategy could fail: whether "how near" constraints and semantic rules generalise past the templates (`PCB_STRATEGY.md:280-304`). A falling share of confident labels on new designs is an early, measurable warning. The industry pattern supports this division of labour. Quilter frames the valuable human work as "deciding intent, constraints, and tradeoffs" ([Quilter](https://www.quilter.ai/blog/the-quilter-interface-comparing-ai-driven-vs-manual-pcb-design-ui)). DeepPCB warns that AI routing can look reasonable while violating "some subtle constraint" ([DeepPCB](https://deeppcb.ai/reinforcement-learning-pcb-routing-explained/)). Both point to AI-assisted intent with deterministic enforcement. The candidate-ranking weights in `kernel.py:231-243` should stay deterministic. Using Jev as a tie-breaker between DRC-clean candidates is possible, but it has low priority until routing quality is measured at all.

## Engineering decisions: Jev as a tripwire, not a decision-maker

Your decision log is already unusually disciplined. It is append-only, and each entry records the decision, the reason, the rejected alternatives and the date. It has two recurring failure modes. Decisions go unlogged (the vLLM provider, AGPL-3.0), and deferred items rely on someone noticing that their trigger fired (criterion 12, the criterion 11 bench test, per-user rate limiting, the Celery solo pool). Both are pattern-recognition problems over commit messages and diffs, and deterministic code handles them badly. Jev handles them cheaply.

**E1 (P1): an unlogged-decision tripwire.** Run it as a pre-push hook or CI step. The state is the commit message plus `git diff --stat` plus the new file headers. Nouls ask "introduces a new external dependency or provider", "changes licensing or distribution terms", and "adds scope listed as Phase 2+ in `.claude/CLAUDE.md`". Any yes with no matching `brain/decisions.md` hunk in the same push fails with a message to log it. This would have caught `11185ff`. Module registration in `regen_state.py` should stay a deterministic AST diff, because code can check it exactly.

**E2 (P1): trigger watchers for deferred decisions.** Convert each deferred item into a typed record with a trigger sentence, and ask Jev one Noul per trigger over recent commits and PR text. For example, "an external person has been or will be shown a generated explanation" fires criterion 12. A yes opens an issue. It never closes the item. This is the one place where Jev's weakness, that it cannot write text, does not matter at all.

**E3 (P3): decision-weight triage.** Use a Choice between one-way door and two-way door ([Farnam Street](https://fs.blog/reversible-irreversible-decisions/)) when a new decision is proposed, and use the answer to set the process: a full log entry with alternatives and a review date for one-way doors, a one-line note for two-way doors. It helps somewhat. The founder's own judgment is usually faster here. Do not use Jev to rank the Phase 2 backlog. Those trade-offs depend on facts only you hold, such as pilot conversations, lab access and runway, and a calibrated classifier with none of that context only adds false precision.

The deterministic judges stay the judges. That covers `ir_validator.py`, `HardwareRuleEngine`, `SimulationGrader` and its 15% tolerance, BOM matching, footprint inference (whose "None when unsure — never a guess" design is correct), firmware template selection, the retry loop's accept/reject decision, and patch application. Jev must never override, soften or skip any of them. Two self-referential weaknesses look like Jev problems but are not. The LLM currently chooses which validation rules run (`ir.validation_rules`), and it also authors the simulation's `expected_outputs`. Fix both deterministically: derive required rules from the IR topology, and compute expected values analytically, as the criterion 11 substitute already does for RC filters. Handing either decision to a second model would add another opinion without adding any ground truth.

## Conclusion

The useful way to think about Jev in Circuit OS is as **asymmetric authority**. It can raise the level of scrutiny: route to review, require simulation, load a stricter rule set, open an issue. It can never lower it. Under that rule, a model that is nine days old, rests largely on snippet-sourced facts and has unmeasured calibration becomes safe to adopt. If Jev is wrong, or down, the worst outcome is an unnecessary review or a skipped optimisation, never an unchecked design. It also points to where the real Phase 2 and Phase 3 risk lies. The gaps Jev fills best (scope enforcement, the out-of-depth signal, net-class labels) exist because the pipeline never decides these things explicitly. Most of the remaining gaps (advisory-only validation, self-chosen rules, self-authored expected outputs) need deterministic fixes, not more AI.

A sensible first week, whichever phase you are really in, has four steps. Reconcile the trackers with where your Phase 2 work actually lives. Log the Jev adoption decision. Build G1 and G2 behind an optional key, with a fallback. Calibrate their thresholds on the existing 20-prompt golden set plus a handful of deliberately out-of-scope prompts. The calibration data will show whether Jev earns the P1 Phase 3 constraint-layer slots, and it is the only evidence on Jev's accuracy that you can fully trust.
