# Agent Bootstrap

> Every agent reads this first. No exceptions.

---

## YOUR FIRST 5 ACTIONS (every session, in order)

```
1. Read   brain/vision.md          ← LAYER 1: what this project is and why
2. Read   brain/architecture.md    ← LAYER 2: modules + data flow
3. Read   plan/current_phase.md    ← what THIS session is about
4. Read   progress.yaml            ← LAYER 4: function-level audited reality
5. Run    git log --oneline -10    ← what actually changed recently
```

After these five steps, you know the project. Do not ask the user to re-explain it.

If you need more depth: `brain/decisions.md` (why choices were made),
`brain/knowledge.md` (domain facts), `brain/timeline.md` (history), `state.json`
(high-level summary), `plan/master_plan.md` (the full roadmap).

---

## TRUST HIERARCHY (when sources disagree, this order wins)

```
1. Test results + simulation outputs    ← highest — reality cannot lie
2. Source code via ast scan             ← function exists or it doesn't
3. progress.yaml + state.json           ← derived from the above two
4. plan/current_phase.md                ← planner's intent
5. brain/*.md files                     ← hints, verify against code
6. Agent-written prose summaries        ← lowest — always verify
```

If `progress.yaml` says a function is `verified_done`, it is.
If it says `broken`, the test is failing — fix the test or fix the code.
If any agent claims something not reflected in `progress.yaml`, do not believe it.

## YOUR ROLE: PLANNER MODE

Activate when: user asks "what should I do next" or "plan the next step"

```
Read:    plan/master_plan.md + plan/current_phase.md + progress.yaml + git log
Infer:   which functions are verified_done / broken / not_started
         (this is in progress.yaml — do not guess)
Output:  next 3 tasks AT FUNCTION LEVEL
         (e.g. "implement simulator.retry_with_options" — not "fix simulator")
         Include: file path, function name, success criterion (which test passes)
Write:   updated task list into plan/current_phase.md
Do not:  write a prose status summary anywhere else
```

The reviewer rule: if `progress.yaml` says a function is `broken` or `not_started`,
the task is not done — regardless of what any previous agent or commit message claimed.

## YOUR ROLE: WORKER MODE

Activate when: user gives you a specific task or says "build X"

```
Read:    plan/current_phase.md  ← your exact tasks at function level
Build:   write code, run tests, fix errors
Test:    pytest tests/  ← every function should have a matching test
                          (parser.parse_nl_to_spec → test_parse_nl_to_spec)
Update:  python tools/regen_state.py  ← MANDATORY at end of session
Commit:  git add -A && git commit -m "session: <brief description>"
```

Never write "I completed X" in a report. Let `regen_state.py` update the state files.

## TESTING CONVENTION (so progress.yaml can map tests to functions)

For every function `foo()` in `src/some_module.py`, write a test `test_foo()` in
`tests/test_some_module.py`. The script matches by name.

Example:
```python
# src/parser.py
def parse_nl_to_spec(text: str) -> dict:
    """Converts natural language → ComponentSpec dict."""
    ...

# tests/test_parser.py
def test_parse_nl_to_spec():
    result = parse_nl_to_spec("RC filter 1kHz")
    assert result["topology"] == "rc_lowpass"
```

When the test passes, `progress.yaml` marks `parse_nl_to_spec` as `verified_done`.
When it fails, marks it `broken`. When the function exists but no test exists, `untested`.
When the function doesn't exist but is in the plan, `not_started`.

- Do not write status updates in prose ("I think parser is done") — run the script
